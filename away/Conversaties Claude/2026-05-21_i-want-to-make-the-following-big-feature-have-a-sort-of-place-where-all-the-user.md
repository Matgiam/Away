Honest answer: **yes, around 200–300 it would start lagging badly, and at 1000 it would freeze on most machines.**

The bottleneck isn't the data layer — `listApprovedCommunityMidis` would pull ~200 KB of JSON for 1000 rows, which is fine. The bottleneck is the **render**:

- Each row uses [`DynamicLiquidGlass`](components/effects/DynamicLiquidglass.tsx:60), which on mount runs a per-pixel canvas pass (~57 000 pixels per row), produces two PNG data URLs, and inserts a unique SVG `<filter>` with `<feDisplacementMap>`/`<feGaussianBlur>` into the DOM. 1000 of those = ~57 M pixel ops on first paint plus 1000 live SVG filters the browser keeps re-evaluating on scroll. That's what kills it.
- Secondary: every node above stays in the DOM (no virtualization), so scrolling is also slow.

Existing built-in songs have the same risk but you control that catalog — community is open submission, so it *will* grow.

Three fixes, cheapest first — want me to do them?

1. **Server-side pagination** in `listApprovedCommunityMidis` — page size 50, infinite-scroll the rest. Cheap, ~30 lines.
2. **List virtualization** for `CommunityView` and `UploadsView` — only render the ~10 visible rows. The other 990 stay as data. Pairs perfectly with #1.
3. **Swap `DynamicLiquidGlass` for a lighter row** (plain `div` with the same gradient + border) when the list passes ~50 items. Keeps the design intact for small lists.

## Net effect at 1000 songs
- Initial load: 1 query → 50 rows, 50 KB.
- Render: ~10 `DynamicLiquidGlass` instances at any time.
- Scroll: paginated 50 at a time, no visible jank.
- Search: one server query per debounced keystroke, returns up to 50 matches across the full library.

## How Transkun actually works (the architecture)

**Stage 1 — Spectrogram.** Audio gets resampled to 44.1 kHz and converted to a log-mel spectrogram: a 2D image where rows are pitches/frequency bins and columns are time frames (~30 ms each). This is the "raw input" the neural network sees.

**Stage 2 — Transformer encoder.** The spectrogram frames go through a Transformer. Self-attention lets every frame "look at" every other frame, so the model knows global context (this matters: a quiet note is easier to detect when the model can see the louder notes before/after it). Output: a context-aware embedding per frame.

**Stage 3 — Interval scoring (this is the key idea).** Instead of asking "is note X on at frame T?" frame-by-frame, Transkun scores **intervals**: for each piano key (88 pitches) and each candidate `(start_frame, end_frame)` pair, it computes "how likely is there a note of this pitch spanning exactly this interval?" Result: a giant 3D score tensor.

**Stage 4 — Semi-CRF decoding (the secret sauce).** Per pitch, find the optimal *non-overlapping* set of intervals using dynamic programming over the interval scores. A semi-CRF maximises the global score, so the model is forced to commit to whole notes as discrete objects. This is why repeated 16th notes don't get smeared into one long note, and sustained notes don't get split into stuttery fragments — both classic Basic Pitch failure modes.

**Stage 5 — Attribute regression.** For each chosen note, separate heads predict:
- Velocity (how hard the key was hit)
- Sub-frame onset offset (so a note can land at ms-level precision, not snapped to the 30 ms frame grid)
- Sub-frame offset (same for release)

**Stage 6 — Output.** A clean list of `(pitch, start_ms, end_ms, velocity)` → standard MIDI file.

**Why this beats Basic Pitch:** Basic Pitch is a small CNN producing three frame-level heatmaps (onsets, frames, contours). A post-processing pass thresholds and glues them into notes — bottom-up. Transkun is top-down: it reasons about notes as units and optimises the whole sequence jointly. The semi-CRF step is what produces the dramatically cleaner timing and the absence of phantom/duplicate notes you noticed.

## 1. What Transkun actually is

Transkun is a **neural network** that converts piano audio into MIDI. It was published by researcher Yujia Yan. The model has three big parts that work together:

### a) Listening to the audio (the encoder)

When you give Transkun an audio file (your MP3), the first thing it does is turn the sound into something a neural network can read: a **spectrogram**. Think of it like a photograph of the audio — the x-axis is time, the y-axis is frequency (low notes at the bottom, high notes at the top), and the brightness of each pixel shows how loud that frequency is at that moment. A 3-minute song becomes an image roughly 6000 pixels wide.

That spectrogram is fed into a **Transformer** — the same family of neural network that powers ChatGPT. The Transformer's superpower is that every part of the input can "pay attention to" every other part. For piano transcription this matters: a quiet note is way easier to identify when the model can see the louder notes that came before and after it. The encoder outputs a richer, context-aware version of the spectrogram.

### b) Scoring every possible note (the interval scorer)

This is where Transkun gets clever. Instead of asking the obvious question — "is note C4 playing at second 12.3?" — Transkun asks something much smarter: **"would there be a note of pitch X spanning from time A to time B?"**

For every piano key (88 of them) and every plausible (start, end) pair, it produces a score. This generates a huge cube of numbers: pitch × start × end, all scored by "how likely is a note here?".

Why this matters becomes obvious in step c.

### c) Picking the best notes (the semi-CRF decoder)

Now Transkun has a giant pile of "maybe-notes" with scores. The job is to pick the *best* set — the ones that actually happened. The naive approach (other models do this) is to grab everything above a threshold. The problem: notes overlap, and two scored candidates of the same pitch might claim overlapping time ranges. Models that just threshold end up producing "stuttering" notes or merging fast repeated notes into one long one.

Transkun uses a **semi-CRF** (semi-Conditional Random Field), which runs a dynamic programming algorithm — like the path-finding algorithm in a GPS. Per pitch, it finds the optimal *non-overlapping* sequence of notes that maximises the total score. So instead of guessing notes one at a time and hoping they fit together, it commits to the whole sequence at once.

**This is the single biggest reason Transkun produces such clean MIDI.** The model is forced to think about whole notes as discrete musical objects, not as patches of "note-is-on" pixels.

### d) Fine-tuning each note (regression heads)

For each chosen note, smaller neural networks predict:
- **Velocity** — how hard the key was pressed (loud or soft)
- **Sub-frame onset** — the exact start time, more precise than the spectrogram's 30 ms frame grid allows
- **Sub-frame offset** — same for the release

Finally those `(pitch, start_ms, end_ms, velocity)` tuples get written to a MIDI file — done.

## 4. The full journey of one upload

Here's exactly what happens when you drop an MP3 in the upload modal:

**Second 0:** You drop the file. `UploadModal.tsx` calls `transcribeAudioToMidi(file, onProgress)`.

**Second 0.01:** `transcribe.ts` sees `NEXT_PUBLIC_TRANSCRIBE_API_URL` is set → calls `transcribeAudioToMidiServer()`.

**Seconds 0-3:** The browser does a `POST https://matgiam-away-transkun.hf.space/transcribe` with the audio file in the request body (as `multipart/form-data`). Your laptop's network connection uploads ~5 MB to Hugging Face's servers. The server saves the file to `/tmp/transkun-jobs/<uuid>/input.mp3` and immediately returns `{ "jobId": "abc-123" }` — *without waiting for transcription*. This is on purpose: HTTP requests time out after ~30 seconds on most networks, but transcription takes minutes.

**Second 3 onwards:** The FastAPI server kicks off `subprocess.run(["transkun", "input.mp3", "output.mid", "--device", "cpu"])` in a background thread. The Python `transkun` library loads its 100+ MB neural network into memory and starts grinding through your audio.

**Meanwhile in the browser:** Your client starts polling every 2 seconds with `GET /jobs/abc-123`. The server responds with `{"status": "running", "progress": 35}`. The client uses this to update the progress bar you see on the modal.

**Seconds 30-300:** The transkun CLI is doing all four neural-network stages I described in section 1 — spectrogram, transformer, semi-CRF decoding, attribute regression. On the free CPU instance HF gives you, this takes 2-5 minutes for a typical song. The output `output.mid` file appears on disk when it's done.

**Final poll:** The server responds `{"status": "done"}`. The client immediately calls `GET /jobs/abc-123/midi`, gets back the binary MIDI file (a few KB), and returns the bytes as an `ArrayBuffer` to `UploadModal.tsx`.

**Wrap-up:** Your existing code parses the MIDI, fills in the form (title, artist, BPM, difficulty), and you click Save. The MIDI ends up in Supabase storage exactly like a manual upload. You can practice it immediately, publish it to the community, or add it to your custom songs. The cleanup job on the server deletes the temp files 30 minutes later.

## 5. Why we made the choices we made

- **Why not run transkun on your laptop?** Because of the chain: transkun needs Python + PyTorch + a C compiler to build one of its dependencies on Windows. That meant installing 8 GB of Visual Studio C++ tools and 2 GB of PyTorch on your school laptop. Cloud sidesteps all of it.

- **Why Hugging Face specifically?** It's free, well-known in the ML world, accepts Docker containers (so we control the environment exactly), and gives us a public HTTPS URL for free. Other options that would work identically: Modal, Railway, Render, Fly.io. HF has the lowest barrier to entry.

- **Why FastAPI?** It's the standard Python HTTP framework right now — async, type-safe, well-documented. Could have used Flask or Django; FastAPI is just smaller and more modern.

- **Why a job-and-poll pattern instead of "submit and wait"?** Because HTTP requests die after about 30 seconds on most networks. A direct request would have to either time out or hang. With the job pattern, the server says "here's your receipt" instantly, and the client checks in periodically. Web crawlers, CI runners, and long-running APIs everywhere use this same pattern.

- **Why Docker?** Two reasons. First, transkun + PyTorch + ffmpeg + sox is a complicated install. Docker lets us declare the whole environment once in a `Dockerfile` and run it identically anywhere — your laptop, HF Spaces, AWS, anywhere. Second, HF Spaces accepts Docker as one of its SDK options, so the same file is the deploy artifact.

- **Why CPU and not GPU?** Free. GPU on HF Spaces costs money. On CPU each transcription takes ~3× the audio length; on GPU it would take seconds. For a school project, free CPU is the right trade-off.

## 6. Things to know

- **First request after idle is slow.** HF puts free CPU containers to sleep after ~30 minutes of no traffic. The next request wakes it up — that takes ~30 seconds before transcription even starts. Subsequent requests on the warm container are fast (no extra startup cost).

- **One transcription at a time.** Your container has one CPU. If two people upload simultaneously, one waits. Fine for a school demo, not for scale.

- **The MIDI quality is real, but not perfect.** Transkun is the current state-of-the-art for piano transcription, but it can still confuse very fast trills, sustain-pedal smears, and clearly non-piano sounds. For solo piano recordings it's outstanding. For piano-with-other-instruments it'll get distracted.

- **HF Spaces is "yours" forever (until you delete it).** It costs nothing to keep running. You can shut it down with a click in Settings if you don't need it anymore, and bring it back later from the same code.

- **The fallback is real.** If you ever delete or break the HF Space, your app keeps working — `transcribe.ts` notices the env var is empty (or the server times out) and silently falls back to Basic Pitch in the browser. Defense in depth.

# What is a neural network?

The shortest honest answer: **a big stack of "voting machines" that learn from examples.**

The longer version, with an analogy:

## Imagine teaching a kid to recognise piano notes by sound

You play a C, and ask "what note?". They guess. You tell them right or wrong. Over thousands of examples, they get better. Their brain has built up a sense of *"that frequency pattern feels like a C"*.

A neural network does the same thing, but with math instead of intuition. Here's how:

### The "neurons"

A neural network is made of layers of **neurons**. Each neuron is incredibly simple — it does **one thing**:

1. Takes a bunch of input numbers
2. Multiplies each by a "weight" (a number the neuron has learned)
3. Adds them up
4. Outputs a single number (after squashing it through a curve like `max(0, x)`)

That's literally it. One neuron is dumb. It can answer "is the input mostly positive or mostly negative?" and not much else.

### The magic of stacking

Stack 100 of those neurons in a row, and you can make slightly more interesting decisions. Stack 100 layers of 1000 neurons each, and connect them so each layer feeds the next, and suddenly you can answer questions like "is this MNIST image a 7?" or "is this audio frame the start of a piano note?".

Each neuron in layer 1 might be detecting things like "is there energy at 440 Hz?". Neurons in layer 2 combine those: "is there energy at 440 Hz AND at 880 Hz?" (that's an A4 + its harmonic — a strong piano-note signal). Layer 3 combines those into "is this an A4 note onset right now?". By the time you reach the last layer, you have abstractions that are useful.

**Nobody told the neurons what to detect.** They figured it out from training data.

### Training: where the learning happens

At the start, all the weights inside the neurons are random — the network is useless. Then you show it 200,000 piano recordings, each labeled with what the correct MIDI is. After each example, you measure how wrong the network was, and you nudge every single weight a tiny amount in the direction that would make the answer less wrong. This is called **backpropagation**.

Do this millions of times across hundreds of GPUs for weeks, and the weights settle into a configuration where the network is *almost always right*. That's a "trained" model. The 100+ MB file Transkun downloads is exactly that: a frozen snapshot of all those weights.

### Why "Transformer" matters

A Transformer is a specific neuron arrangement invented in 2017. Its trick is **attention**: every neuron in a layer can look at every other neuron in the previous layer and decide which ones to pay attention to. Older networks (like CNNs, which Basic Pitch uses) can only look at neighbours.

For piano transcription, this means a Transformer can hear a quiet note at second 30 and check "wait, did I hear this same pitch at second 25? That helps me decide if this is real or just noise." A CNN can only look ~1 second around the current frame.

That's it. That's neural networks. They're not magic; they're just very large, very well-tuned weighted sums of numbers — but the scale (billions of operations per inference) is what makes them feel intelligent.

# Technische synthese — *Away*

## 1. Overzicht

*Away* is een webapplicatie waarmee gebruikers piano kunnen spelen, alleen of samen met anderen in real-time, alsook gestructureerd kunnen oefenen aan de hand van bladmuziek, lessenreeksen en eigen MIDI-bestanden. De applicatie is volledig browser-gebaseerd en vereist geen installatie van software langs de kant van de gebruiker.

Het project bestaat uit drie afzonderlijke componenten die met elkaar communiceren over HTTPS:

1. **Een Next.js-frontend** (gehost op Vercel) die de volledige gebruikersinterface, de audio-engine en de muzikale logica bevat.
2. **Een Supabase-backend** voor authenticatie, gegevensopslag (PostgreSQL) en bestandopslag (audio en MIDI).
3. **Een Python-microservice op Hugging Face Spaces** voor het transcriberen van audio naar MIDI met behulp van een transformer-gebaseerd neuraal netwerk (Transkun).

## 2. Architectuur

```
Browser (Next.js + React)
   │
   ├──► Supabase  (authenticatie, PostgreSQL, Storage, RLS)
   │
   ├──► Hugging Face Space  (Docker + FastAPI + PyTorch + Transkun)
   │
   └──► WebRTC peer-to-peer  (multiplayer, real-time)
```

Het ontwerp volgt het principe van **gracieuze degradatie**: als de transkun-server niet beschikbaar is, valt de applicatie automatisch terug op een lichter in-browser model (Basic Pitch). Als de gebruiker niet is ingelogd, blijven de niet-persoonlijke functionaliteiten (de standaardpiano, ingebouwde liederen) toegankelijk.

## 3. Frontend

- **Framework**: Next.js 15 (App Router) met React 19 en TypeScript.
- **Styling**: Tailwind CSS 4. Aangepaste visuele effecten zoals *Liquid Glass* (gerealiseerd via SVG-filters en `feDisplacementMap`) en een geanimeerde *Silk Background*.
- **Audio-engine**: Tone.js met een `Sampler` die meerdere soundfonts ondersteunt (Salamander Grand Piano, harpsichord, e.a.). De audio-context wordt gedeeld over de hele applicatie via een `AudioEngineProvider` (React Context).
- **Invoermethoden**: hardware-MIDI (Web MIDI API), computertoetsenbord (configureerbare *keybindings* met meerdere lay-outpresets) en muis/touch.
- **Visualisatie**: vallende noten gerenderd via React met `requestAnimationFrame`. Voor langere lijsten (de community-bibliotheek) wordt **virtualisatie met vast-hoogte rijen** toegepast — slechts ongeveer tien rijen worden tegelijk in de DOM gehouden, zodat duizenden vermeldingen niet voor een prestatieprobleem zorgen.

## 4. Backend — Supabase

- **Authenticatie**: e-mail/wachtwoord en Google OAuth via Supabase Auth. Sessies via HTTP-only cookies (SSR-veilig via `@supabase/ssr`).
- **PostgreSQL-tabellen** (niet-uitputtend): `profiles`, `friendships`, `user_stats`, `user_song_uploads`, `community_midis`, `community_midi_additions`, `recordings`, `achievements`.
- **Storage-buckets**: `midi_uploads` (privé per gebruiker), `community_midis` (publiek, na goedkeuring), `recordings` (privé).
- **Row-Level Security (RLS)**: elke tabel is afgeschermd via *policies* die de leesbaarheid en schrijfbaarheid afhankelijk maken van `auth.uid()`. Bijvoorbeeld: alleen goedgekeurde community-MIDI's zijn voor alle ingelogde gebruikers zichtbaar; pending submissions blijven beperkt tot de indiener en de admin (`profiles.is_admin = TRUE`).
- **RPC-functies**: enkele atomische operaties (zoals het verhogen van een afspeelteller) worden uitgevoerd via `SECURITY DEFINER`-functies in PostgreSQL om race conditions te vermijden.

## 5. Multiplayer

Real-time noot-uitwisseling tussen spelers gebeurt **peer-to-peer via WebRTC**. Supabase dient enkel als signaleringskanaal (om de initiële verbindingen op te zetten). Eens de WebRTC-kanalen tot stand komen, vloeit het verkeer rechtstreeks tussen de browsers — wat de latentie aanzienlijk verlaagt, kritisch bij het samen spelen van muziek.

Een `PresenceProvider` (gebaseerd op Supabase Realtime) houdt bij welke gebruikers online zijn en in welke kamer ze zich bevinden, voor de online-status-indicatoren en vriendlijst.

## 6. Audio-naar-MIDI-transcriptie

Twee onafhankelijke transcriptie-engines zijn beschikbaar, met de keuze aan de gebruiker:

### 6.1. Basic Pitch (browser, snel)

Het kleine CNN-model van Spotify (~2 MB), draaiend in TensorFlow.js. Verwerking gebeurt volledig client-side, in ongeveer 30 seconden per nummer. Goede kwaliteit voor eenvoudige melodieën, maar gevoelig voor *stutter* bij snelle herhaalde noten.

### 6.2. Transkun (server, hoge kwaliteit)

Het onderzoek-grade model van Yujia Yan, gebaseerd op:

1. **Mel-spectrogram** van het invoer-audio (44,1 kHz).
2. **Transformer-encoder** die elke tijdframe in een contextuele *embedding* omzet (self-attention over de volledige duur).
3. **Interval-scorer**: voor elke toonhoogte (88 pianotoetsen) en elk plausibel `(begin, einde)`-paar wordt een score berekend.
4. **Semi-CRF-decoder**: dynamisch programmeren kiest per toonhoogte de globaal optimale, niet-overlappende verzameling intervallen — de cruciale innovatie die kwalitatief veel netter MIDI oplevert dan frame-gebaseerde modellen.
5. **Regressie-koppen** voor velocity en sub-frame onset/offset-offsets.

Aangezien Transkun een PyTorch-model van ruim 100 MB is dat niet in de browser kan draaien, werd hiervoor een aparte microservice opgezet:

- **FastAPI**-server in een Docker-container.
- **Job-pattern** met asynchrone verwerking: de browser laadt het audio op (`POST /transcribe` → `{ jobId }`), pollt vervolgens elke 2 seconden (`GET /jobs/{id}`) en download het resultaat (`GET /jobs/{id}/midi`) zodra de status `done` is. Dit ontwijkt de standaard HTTP-timeout van ~30 seconden.
- **Hugging Face Spaces** (gratis CPU-tier) als hostingplatform — Docker-container, één publieke HTTPS-endpoint, geen onderhoud.
- **CORS** + optionele `X-API-Key`-header als beveiliging.

## 7. Communautaire MIDI-bibliotheek

Gebruikers kunnen zelf-geüploade MIDI-bestanden indienen voor publicatie. Het werkproces:

1. De gebruiker klikt **Publish** op een privé-upload. Het bestand wordt gekopieerd van de `midi_uploads`-bucket naar de `community_midis`-bucket; een nieuwe rij wordt aangemaakt met `status = 'pending'`.
2. Op de **administratiepagina** (`/admin/midi-review`, beschermd door `is_admin`-vlag) krijgt de admin een overzicht van alle hangende indieningen, kan hij elk bestand volledig afspelen via de bestaande audio-engine, en de aanvraag aanvaarden of afwijzen (met optionele reden).
3. Na goedkeuring wordt het MIDI publiek toegankelijk voor alle ingelogde gebruikers in de **Community**-categorie van de praktijkmodus.

Elk MIDI heeft een **3-secondenpreview** beschikbaar via een afspeelknop — een lichtgewicht functie die de eerste noten van het bestand decodeert en via de bestaande Tone.js-engine afspeelt.

Goedgekeurde bestanden kunnen door elke gebruiker worden **toegevoegd aan zijn persoonlijke "Custom"-categorie** via een junction-tabel (`community_midi_additions`), zonder duplicatie van het bestand zelf.

## 8. Belangrijkste technische keuzes en hun motivatie

| Keuze | Motivatie |
|---|---|
| **Next.js (App Router)** | Server-side rendering voor SEO, ingebouwde routing, statische assets, eenvoudige integratie met Vercel. |

## 10. Schaalbaarheid en limieten

- **Frontend**: zonder beperking; Vercel schaalt automatisch.
- **Supabase**: gratis tier ondersteunt tot 500 MB database en 1 GB storage — voldoende voor een schoolproject. RLS-policies zijn correct geïndexeerd om bevragingen op de community-tabel snel te houden.

# Technisch onderzoek — *Away*

Voor dit eindwerk heb ik bij elke technische keuze meerdere alternatieven afgewogen. Hieronder licht ik per onderdeel toe wat het is, welke alternatieven ik heb overwogen, en waarom ik uiteindelijk voor deze technologie heb gekozen.

---

## 1. Frontend-framework — Next.js

### Wat?

Next.js is een React-framework dat zowel server-side rendering (SSR) als static site generation (SSG) ondersteunt. Het wordt ontwikkeld door Vercel en is sinds versie 13 gebaseerd op de App Router-architectuur met React Server Components.

### Waarom?

Ik heb drie frameworks vergeleken: **Next.js**, **SvelteKit** en **vanilla React (Vite)**. Next.js won om drie redenen:

1. **Native ondersteuning voor server-side rendering**, wat cruciaal is voor de SEO van de homepage en de praktijkpagina's. Vanilla React kan dit niet zonder externe configuratie.
2. **Ingebouwde routing en API-routes**, terwijl ik bij vanilla React `react-router` en een aparte backend had moeten opzetten.
3. **Directe integratie met Vercel** (de hostingsdienst van dezelfde maker), waardoor zero-configuratie deployment mogelijk is met previews per pull request.

SvelteKit is technisch elegant maar heeft een veel kleinere community en geen partnership met Supabase via een officieel SDK-pakket.

### Voordelen

1. Server-side rendering uit de doos
2. Ingebouwde routing (App Router)
3. Massieve community en ecosysteem
4. Officiële Vercel-integratie
5. Officiële Supabase-SDK (`@supabase/ssr`)

### Nadelen

1. Steile leercurve voor de App Router (Server vs Client Components)
2. Build-tijd hoger dan SvelteKit
3. Vendor lock-in richting Vercel voor optimaal gebruik

---

## 2. Type-systeem — TypeScript

### Wat?

TypeScript is een superset van JavaScript die statisch typeren toevoegt. Code wordt naar JavaScript gecompileerd voordat hij in de browser draait.

### Waarom?

Het alternatief was **gewoon JavaScript**. Voor een project van deze schaal (40+ React-componenten, een audio-engine met meerdere lagen, een database met tien tabellen) was typeveiligheid niet optioneel. Eén verkeerd doorgegeven veld in de Supabase-tabel `community_midis` zou anders pas zichtbaar zijn in productie. Met TypeScript vangt de compiler dit op voordat de code wordt geladen.

### Voordelen

1. Foutdetectie tijdens het schrijven
2. Auto-completion in de IDE
3. Gemakkelijker refactoren in grote codebases
4. Documenteert het contract van elke functie

### Nadelen

1. Extra compilatiestap
2. Soms vermoeiend voor snelle prototypen
3. Sommige bibliotheken hebben onvolledige type-definities

## 3. Backend & database — Supabase

### Wat?

Supabase is een open-source backend-as-a-service die PostgreSQL, authenticatie, bestandsopslag en realtime-subscripties combineert in één beheerde dienst.

### Waarom?

Ik heb drie opties vergeleken: **Supabase**, **Firebase** en een **eigen Node.js + PostgreSQL-backend met phpMyAdmin**.

Een **eigen backend** zou betekenen dat ik zelf de authenticatie, RESTful API, bestandsopslag, en hostingen had moeten bouwen — minstens twee weken werk voor functionaliteit die niet de kern van mijn project is. **phpMyAdmin** is enkel een database-interface en biedt geen authenticatie of API.

**Firebase** is een aantrekkelijk alternatief, maar gebruikt een NoSQL document-database (Firestore). Voor relationele gegevens zoals vriendschappen tussen gebruikers, of community-MIDI's met meerdere afgeleide relaties, is een echte SQL-database veel geschikter.

**Supabase** combineerde alles wat ik nodig had en heeft bovendien een officiële SDK voor Next.js (`@supabase/ssr`), wat de setup tot minder dan tien regels code reduceerde.

### Voordelen

1. Echte PostgreSQL-database (niet NoSQL)
2. Row-Level Security regelt toegangsrechten op databasenivo
3. Authenticatie (e-mail, Google) inbegrepen
4. Bestandsopslag inbegrepen (`midi_uploads`, `community_midis`)
5. Realtime-subscripties voor multiplayer-presence
6. Officiële Next.js-integratie
7. Royaal gratis plan (500 MB DB + 1 GB storage)
8. Type-veilige queries

### Nadelen

1. Vendor lock-in (al is migratie naar standaard PostgreSQL mogelijk)
2. Free tier slaapt na een week inactiviteit (project moet wakker worden gemaakt)
3. RLS-policies hebben een leercurve

## 4. Styling — Tailwind CSS

### Wat?

Tailwind is een utility-first CSS-framework. In plaats van eigen CSS-klassen te schrijven, gebruik je vooraf gedefinieerde utility-klassen direct in de HTML (`flex`, `text-white/80`, `rounded-xl`).

### Waarom?

Ik heb drie methoden afgewogen: **Tailwind**, **styled-components** en **gewone CSS-modules**.

**Styled-components** is elegant maar voegt runtime-overhead toe en heeft slechte ondersteuning in React Server Components. **CSS-modules** zijn lichter maar dwingen je om voor elke component een aparte stylesheet te beheren, wat het ontwerpiteratieproces vertraagt.

**Tailwind** liet me toe om direct in de JSX te ontwerpen zonder context-switching. De PostCSS-build verwijdert alle ongebruikte klassen, waardoor de finale CSS-bundel kleiner is dan handmatig geschreven CSS.

### Voordelen

1. Geen aparte CSS-bestanden nodig
2. Tree-shaking verwijdert ongebruikte stijlen
3. Consistente design tokens (kleuren, ruimte, typografie)
4. Snel itereren tijdens ontwerp
5. Native Next.js-integratie

### Nadelen

1. Lange utility-rijen kunnen onleesbaar worden
2. Leercurve voor de naamgevingsconventies
3. Niet ideaal voor zeer complexe animaties (daar gebruik ik CSS-in-JS)

## 5. Audio-engine — Tone.js

### Wat?

Tone.js is een framework bovenop de Web Audio API, gericht op muzikale toepassingen. Het biedt klassen voor *Samplers*, *Synthesizers*, *Effects* en een gesynchroniseerde *Transport*.

### Waarom?

De drie opties waren: **directe Web Audio API**, **Tone.js**, of **Howler.js**.

**Web Audio API direct** is krachtig maar zeer laag-niveau — voor het bouwen van een Sampler die honderden noten cross-fade, zou ik enkele honderden regels boilerplate moeten schrijven. **Howler.js** is gemaakt voor game-audio (geluidseffecten, niet melodisch werk) en heeft geen begrip van noten, octaaf-stijgingen of velocity.

**Tone.js** is specifiek voor muziek-applicaties ontworpen. De `Sampler`-klasse laadt automatisch sample-bestanden voor elke noot, met interpolatie voor tussenliggende toonhoogtes — exact wat ik nodig had voor een realistische pianoklank.

### Voordelen

1. Hoog-niveau abstractie speciaal voor muziek
2. Automatische sample-loading met interpolatie
3. Ingebouwde effecten (reverb, volume, sustain)
4. Sample-accurate timing via een eigen *scheduler*
5. Bekende standaard in webaudio-projecten

### Nadelen

1. Bundlegrootte aanzienlijk (~200 KB gzipped)
2. AudioContext moet door een gebruikersgebaar geactiveerd worden (browserveiligheid)
3. Soms onhandig debugging vanwege async sample-loading

## 6. Multiplayer-architectuur — WebRTC peer-to-peer

### Wat?

WebRTC laat browsers direct met elkaar communiceren via een gecodeerde peer-to-peer-verbinding, zonder dat een centrale server in het midden zit. Een signaleringskanaal is enkel nodig om de initiële verbinding op te zetten.

### Waarom?

Ik had twee opties: **WebRTC P2P** of **WebSockets via een relay-server** (bijv. Socket.io).

Voor het synchroniseren van noten tussen twee pianisten in real-time is **latentie cruciaal**. Een WebSocket-relay voegt twee netwerk-hops toe (speler → server → andere speler). Met WebRTC gaat het rechtstreeks, wat afhankelijk van de afstand 50-200 ms scheelt — een hoorbaar verschil bij het samen spelen.

Een tweede argument: een WebSocket-relay zou continue bandbreedtekosten genereren bij hostingdiensten. WebRTC P2P kost niets eens de verbinding is opgezet.

Ik gebruik **Supabase Realtime** als signaleringskanaal (gratis), wat de oplossing volledig gratis houdt.

### Voordelen

1. Minimale latentie (geen tussenstop)
2. Geen bandbreedtekosten
3. Eind-tot-eind versleuteld
4. Schaalbaar zonder server-upgrade

### Nadelen

1. Complexere setup (ICE, STUN, NAT-traversal)
2. Werkt soms niet door strikte firewalls (~5% van de gebruikers)
3. Geen centrale logging mogelijk

## 7. Hoge-kwaliteit transcriptie — Transkun

### Wat?

Transkun is een neuraal netwerk voor pianotranscriptie, gebaseerd op een Transformer-encoder en een semi-CRF-decoder. Het werd in 2024 gepubliceerd door onderzoeker Yujia Yan en is state-of-the-art op de MAESTRO-benchmark.

### Waarom?

Voor audio-naar-MIDI-transcriptie heb ik drie modellen overwogen: **Basic Pitch** (Spotify), **Onsets-and-Frames** (Google Magenta) en **Transkun**.

**Basic Pitch** is klein genoeg om in de browser te draaien (TensorFlow.js, ~2 MB), maar de kwaliteit is matig: het verwart snelle herhaalde noten en breekt aangehouden noten op in fragmenten.

**Onsets-and-Frames** is beter dan Basic Pitch maar gebruikt nog steeds een frame-gebaseerde aanpak die soortgelijke fouten maakt.

**Transkun** is fundamenteel anders: het redeneert over hele noten als discrete objecten dankzij zijn semi-CRF-decoder die globale optimalisatie toepast via dynamisch programmeren. Het resultaat is dramatisch netter — geen *stutter*, geen valse splitsingen.

### Voordelen

1. State-of-the-art kwaliteit op de MAESTRO-benchmark
2. Voorgetraind checkpoint beschikbaar
3. Open-source (PyTorch)
4. Sub-frame timing-precisie via regressie-koppen

### Nadelen

1. Kan niet in de browser draaien (PyTorch)
2. Vereist een server (extra deployment-stap)
3. Verwerkingstijd 2-5 minuten per nummer op CPU
4. Modelbestanden 100+ MB

## 8. Snelle in-browser transcriptie — Basic Pitch

### Wat?

Basic Pitch is een klein CNN-model van Spotify dat audio omzet naar MIDI, ontworpen om in TensorFlow.js te draaien.

### Waarom?

Hoewel Transkun de beste kwaliteit biedt, duurt het 2-5 minuten per nummer. Sommige gebruikers willen een **snel resultaat van mindere kwaliteit** in plaats van te wachten. Ik bied beide engines aan met een keuzemenu in de upload-modal:

- **Basic Pitch** (snel, 30 s, in browser)
- **Transkun** (traag, 3 min, op server)

Op die manier valt de applicatie ook automatisch terug op Basic Pitch als de Transkun-server niet beschikbaar is — *graceful degradation*.

### Voordelen

1. Volledig in de browser (geen server nodig)
2. Snelle verwerking (~30 s)
3. Klein modelbestand (~2 MB)
4. Gratis fallback als de hoofdserver uitvalt

### Nadelen

1. Mindere kwaliteit dan Transkun
2. Vereist Web Audio API (niet alle oude browsers)

## 9. Hosting van de transcriptie-server — Hugging Face Spaces

### Wat?

Hugging Face Spaces is een hostingsdienst voor machine learning-toepassingen die Docker-containers ondersteunt en een gratis CPU-tier biedt.

### Waarom?

Vier hostingsdiensten kwamen in aanmerking: **Hugging Face Spaces**, **Modal**, **Railway** en **een eigen VPS bij DigitalOcean**.

**Een eigen VPS** vereist creditcard, kost minstens €5/maand, en zou Linux-beheer betekenen (security updates, firewall, monitoring) — overkill voor een eindwerk.

**Railway** is uitstekend maar het gratis aanbod is recent ingetrokken; nieuwe accounts moeten betalen.

**Modal** heeft een gratis tier maar vereist een aparte SDK en is meer gericht op cron-taken dan op HTTP-servers.

**Hugging Face Spaces** is gratis, vereist geen creditcard, accepteert Dockerfiles direct, en is de bekende standaard voor machine learning-deployment. De build-logs zijn zichtbaar in de webinterface, wat debugging vergemakkelijkt.

### Voordelen

1. Volledig gratis CPU-tier
2. Geen creditcard nodig
3. Directe Docker-ondersteuning
4. Build- en runtime-logs in de browser
5. Automatische HTTPS-endpoint

### Nadelen

1. Containers slapen na ~30 min inactiviteit (cold start van ~30 s)
2. Slechts één CPU-kern op de gratis tier
3. Geen persistente schijfopslag op de gratis tier

## 10. Web-framework van de transcriptie-server — FastAPI

### Wat?

FastAPI is een moderne Python-webframework gebaseerd op asynchrone routes en automatische OpenAPI-documentatiegeneratie via Pydantic-typehints.

### Waarom?

De alternatieven waren **Flask** (klassiek, synchroon) en **Django REST Framework** (zwaar, gericht op grote applicaties).

**Flask** kan synchroon blijven, wat voor een lange transcriptie-taak (3 minuten) problematisch is. Met FastAPI kan ik de upload streamen en de transcriptie als achtergrondtaak starten zonder de verbinding open te houden.

**Django REST Framework** is overdreven voor een service met drie endpoints; bovendien zou de Docker-image dubbel zo groot zijn.

### Voordelen

1. Native async-ondersteuning
2. Type-veilige routes via Pydantic
3. Automatische OpenAPI-documentatie
4. Hoge prestatie (Starlette + Uvicorn)
5. Minimaal aantal afhankelijkheden

### Nadelen

1. Jongere ecosysteem dan Flask of Django
2. Async-paradigma vereist gewoonte

## 11. Containerisering — Docker

### Wat?

Docker pakt een applicatie samen met al zijn afhankelijkheden in een lichtgewicht, draagbare container die op elke moderne Linux-server kan draaien.

### Waarom?

Het alternatief was **direct met Python en pip op de hostmachine** te werken. Drie problemen:

1. **PyTorch heeft een specifieke versie nodig** die conflicteert met andere Python-projecten op dezelfde machine.
2. **Transkun heeft systeem-afhankelijkheden** (`ffmpeg`, `sox`, `libsndfile`) die op elke server apart geïnstalleerd moeten worden.
3. **Reproduceerbaarheid**: een container die lokaal werkt, werkt ook op Hugging Face Spaces.

De Dockerfile is bovendien een vereiste voor een Docker Space.

### Voordelen

1. Reproduceerbare omgeving over alle machines
2. Isolatie van systeem-afhankelijkheden
3. Eén artefact, overal te draaien
4. Vereist door Hugging Face Spaces

### Nadelen

1. Build-tijd ~10-15 min (PyTorch is groot)
2. Image-grootte ~2 GB
3. Leercurve voor wie nieuw is met containers

## 12. Hosting van de frontend — Vercel

### Wat?

Vercel is de hostingsdienst van de Next.js-makers. Het biedt automatische deployments, edge-functies, en een geïntegreerde CDN.

### Waarom?

Drie hostingsplatforms vergelijken: **Vercel**, **Netlify** en **Cloudflare Pages**.

**Netlify** is een goed alternatief maar heeft minder geoptimaliseerde Next.js-ondersteuning — sommige App Router-features werken niet of vereisen workarounds.

**Cloudflare Pages** is technisch indrukwekkend maar de Next.js-integratie is via een adapter en niet alle features zijn ondersteund.

**Vercel** wordt gemaakt door dezelfde mensen als Next.js — alles werkt zonder configuratie. Eén `git push` en de site staat live met een preview-URL per branch.

### Voordelen

1. Zero-config Next.js-deployment
2. Automatische previews per pull request
3. Geïntegreerde CDN (snel wereldwijd)
4. Edge-functies inbegrepen
5. Gratis tier ruim voldoende

### Nadelen

1. Vendor lock-in
2. Build-minuten beperkt op gratis tier
3. Sommige geavanceerde features alleen op betalende tiers

## 6. Hardware-keyboardondersteuning — Web MIDI API

### Wat?

De Web MIDI API is een ingebouwde browser-API waarmee een webpagina rechtstreeks kan communiceren met aangesloten MIDI-apparaten (USB-keyboards, MIDI-controllers, sustainpedalen). De pagina ontvangt elke noot, velocity en pedaalbeweging als een event, met dezelfde precisie als een desktop-applicatie.

### Waarom?

Voor serieuze pianisten is spelen met een fysiek MIDI-keyboard onvervangbaar — de aanslaggevoeligheid, het 88-toetsen-bereik en de sustainpedaal kunnen niet nagebootst worden met een computertoetsenbord. Ik heb drie opties afgewogen om hardware-input te ondersteunen:

1. **Enkel computertoetsenbord-input** — werkt out-of-the-box maar verliest velocity, sustain en het volledige toetsenbereik. Geen echte optie voor iemand die echt piano speelt.
2. **Bluetooth MIDI via externe bibliotheken** — kan in theorie werken, maar de browserondersteuning is fragmentarisch en de latentie is hoger dan bij USB.
3. **Native Web MIDI API** — wordt direct ondersteund in Chrome, Edge en Opera, vereist geen installatie van drivers, en geeft sub-milliseconde latentie via USB. De API levert alle standaard-MIDI-berichten: `noteOn`, `noteOff`, `velocity`, `sustain` (CC64), `modulation` (CC1), `pitch bend`.

De Web MIDI API was de logische keuze: ze is **native** (geen externe bibliotheek nodig), heeft de **laagste latentie** (geen extra abstractielaag tussen het apparaat en de audio-engine) en werkt met **elk USB-MIDI-apparaat zonder drivers**.

In de praktijk wordt elke binnenkomende noot doorgegeven aan dezelfde callback (`handleNotePlayed`) die het computertoetsenbord gebruikt — voor de audio-engine en de visualizer is er geen verschil tussen "speler drukte een fysieke toets in" en "speler typte op zijn laptop". Dit hield de code-architectuur eenvoudig.

### Voordelen

1. Native browser-ondersteuning (geen externe bibliotheek)
2. Sub-milliseconde latentie via USB
3. Werkt met elk standaard USB-MIDI-keyboard zonder drivers
4. Ondersteunt volledige MIDI-specificatie (velocity, sustain, modulation, pitch bend)
5. Geen installatie nodig aan de kant van de gebruiker

### Nadelen

1. Standaard niet ondersteund in Firefox (vereist een experimentele flag)
2. Niet beschikbaar in Safari op iOS
3. Vereist eenmalige toestemming van de gebruiker (zoals microfoon-toegang)
4. Hot-plug detectie werkt niet betrouwbaar in alle browsers — soms moet de pagina vernieuwd worden na het aansluiten van een nieuw apparaat

### 2.3 Multiplayer — een kamer aanmaken of een kamer betreden

#### Een nieuwe kamer aanmaken

1. Klik op **Multiplayer mode** vanaf de homepagina.
2. Klik op de knop **Create room**.
3. Stel de kamer in:
   - **Toegankelijkheid**:
     - **Public** — iedereen kan de kamer zien en deelnemen.
     - **Private** — alleen mensen met het wachtwoord kunnen deelnemen.
     - **Friends** — alleen je vrienden kunnen de kamer zien en deelnemen.
   - **Wachtwoord** (alleen bij Private) — kies een wachtwoord van minstens 4 tekens.
   - **Maximum aantal spelers** — tussen 2 en 8.
4. Klik op **Next** en geef de kamer een **naam** (bijv. *"Chopin Nocturne Jam"*).
5. Klik op **Create**. Je wordt automatisch naar de kamer gestuurd.

#### Een bestaande kamer betreden

1. Vanaf de Multiplayer-pagina zie je de lijst met **publieke kamers** en de kamers van je vrienden.
2. Klik op een kamer om deze te betreden.
3. Bij een **private kamer** wordt het wachtwoord gevraagd. Vul het in en klik **Join**.

#### In de kamer

- Iedereen ziet en hoort de noten van de andere spelers in **real-time** (via een directe peer-to-peer-verbinding).
- Elke speler heeft een **eigen kleur**; noten van anderen verschijnen in hun kleur op de visualizer.
- Een **chatvenster** (rechtsonder) laat je tekstberichten uitwisselen.
- De **deellink** (boven de chat) kun je kopiëren en met iemand delen om hem direct toe te laten — handig voor private kamers.

#### Een kamer verlaten

Klik op de **pijl** linksboven om terug naar de Multiplayer-startpagina te gaan. Als jij de eigenaar was en er nog spelers in de kamer zijn, blijft de kamer bestaan; anders wordt ze automatisch opgeruimd.

#### Vrienden toevoegen

Om de **Friends-only**-functie te gebruiken, voeg je eerst vrienden toe:
1. Ga naar je **profielpagina** (homepagina → Profile).
2. Open het **Friends**-paneel.
3. Zoek een gebruikersnaam en klik op **+ Add friend**.
4. De andere gebruiker krijgt een verzoek en moet dit aanvaarden voor de vriendschap actief wordt.
